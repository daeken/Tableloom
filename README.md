# Tableloom

A self-hosted, web-based virtual tabletop for the systems you actually play. TypeScript throughout, a shared sketchable battlefield, and code-first game modules with custom sheets, rules, and content packs.

**Status:** authenticated tabletop with object permissions, private rolls, and shared/private note documents. Returning-player recovery, member/invitation management, and GM ownership reassignment are available. Campaign management/selection APIs and isolated live rooms are available, with exact package pins and campaign-scoped credentials. The browser has campaign selection/settings, GM scene controls, and version-checked scene edits with conflict feedback, drawing/token multi-selection, atomic mixed movement/deletion, optional local grid snapping, and durable member-scoped scene-edit undo/redo. Versioned module-backed document storage/APIs, explicit GM schema migrations, and roll-history archive/cleanup controls are available; browser sheets remain queued. This README is the authoritative work queue. Cyberpunk RED, Kids on Bikes, and Kids on Brooms are the initial module targets; their rulebooks have not been supplied and no published mechanics or catalog content are implemented yet.

## Run locally

Requires Node.js 24 and npm. No database service or external account is required.

```sh
npm ci
npm run dev
```

Open http://localhost:5173. On first launch, create the host using the private key in `data/host-key` (or your configured `TABLELOOM_HOST_KEY`). The server prints the file location, never the key itself. Keep this key private: it can also recover the host identity after signing out or losing a session. Existing prototype scene data is retained.

Once signed in, the host can choose **Invite & players**, create a one-use code, and share the table address and code with a friend. The friend enters a name and that code. Use separate browser profiles to test independent identities; ordinary tabs share a browser session. A player cannot create invitations.

Sessions last seven days and survive server restarts. Signing out revokes the session and clears the browser table. The host can select **I'm the host** to recover access with the private key. For a returning player, the GM opens **Invite & players** and chooses **Create return code** beside their existing membership. The player enters that code on the same join screen; their original identity, name, object ownership, private notes, and private rolls are preserved. The name entered on the join screen is used only for new-player invitations. Issuing a new return code replaces that player’s previous unused return code; using it signs out all of their previous sessions. Codes expire after one day and work once. Names alone never recover an identity.

The development server proxies `/api` and the WebSocket to Fastify on port 3001. The browser opens the campaign selected by its session and that campaign’s active scene. New invitations enter their own campaign; host setup/recovery opens the default campaign. Use the campaign name in the header to select/create a campaign, edit its settings as GM, or join another invitation under your existing identity. The campaign and active-scene headings update live. GMs can open **Manage scenes**, create an empty offstage scene, and review **Show scene to everyone** to move the whole campaign to it. Each scene retains its own drawings/tokens; campaign notes and rolls stay available. Save drafts before changing campaigns. In-memory note drafts survive scene changes, while unfinished canvas gestures/selection reset. SQLite data lives in `data/tableloom.sqlite` (ignored by Git).

```sh
npm run check       # strict types, tests, build, production smoke check
npm run build
npm start           # frontend + API on http://127.0.0.1:3001
```

Configuration: `PORT` (default `3001`), `HOST` (default `127.0.0.1`), `DATA_DIR` (default `./data`), optional `TABLELOOM_HOST_KEY` (32–512 characters, otherwise a random key is generated in a private `host-key` file), and optional `PUBLIC_ORIGIN` (the browser-facing HTTP(S) origin, without a path). For an HTTPS reverse proxy, set `PUBLIC_ORIGIN=https://your-table.example`; this enforces the configured origin and enables Secure session cookies without trusting forwarded headers. Development defaults to same-origin HTTP on loopback.

Only authenticated members can fetch or connect to the table. Everyone can draw, create tokens, and roll dice. Players can move/delete their own tokens and delete their own drawings; the GM can edit every object and change the game system. The server assigns ownership to the creator; creation commands reject caller-supplied ownership. Older objects without a recorded owner stay under GM control until assigned. The GM can select **Manage ownership** below the cast list, choose a token/drawing/note and a current member, then review and confirm the transfer. Removed members cannot receive ownership. Assigning an object to the GM keeps it under GM control.

Scene objects are currently public to all table members. Before rolling, choose **Everyone at the table** or **You and the GM**. Private rolls are visible only to the roller and the GM; a GM's private rolls stay with the GM. The history marks private results explicitly. Public is the default, and already-recorded roll visibility cannot be changed. Sign-out/identity changes clear the local roll draft.

The **Notes** panel supports plain-text documents. **New** creates a private note visible to its owner and the GM; GM-owned private notes stay with the GM. Set **Who can read this?** to **Everyone at the table** and save to share a note. Other players can read shared notes; only the owner and GM can edit or delete them. Changing a note back to private removes it from other players' current/future views. Previously shared text may already have been read.

Note edits require **Save changes**. Unsaved drafts stay in memory when switching notes/tabs and through unrelated table updates; save before reloading or signing out. Clean editors follow remote saves. If another editor saves while you have a draft, your draft is retained and stale saves/deletes are blocked until you explicitly reload the latest version. Notes are limited to 100 per campaign, 120 characters per title, and 10,000 characters per body.

The GM can list members and unused codes, revoke codes, and remove players in **Invite & players**. Member/code lists never return saved bearer credentials; a newly issued code is displayed only in its issuing dialog. Removing a player immediately revokes their sessions and return codes. Their existing objects, notes, and rolls remain stored and available to the GM; removal does not reassign or publish them. A fresh invitation creates a different identity, even with the same name. The host cannot be removed. Backing up the private host key still needs a complete backup/recovery procedure. Module-backed documents have a separate API described below; character-sheet UI, rich text, attachments, and version history are not implemented yet.

Note transfers keep the saved content and visibility. A private note requires explicit confirmation before the new owner receives its full saved text and the previous player owner loses access. The GM always retains access. A public note stays readable by the table, but edit/delete rights move to the new owner. Transfers advance the note version, blocking stale edits/deletes; the review screen blocks confirmation if the note changes while being reviewed. Save drafts before transferring. Hidden notes and their local drafts disappear from the previous player’s current view; previously read content cannot be recalled. Dice results keep their original ownership and attribution. Ownership transfers have no dedicated history or undo yet.

## Architecture

| Location                 | Responsibility                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| `apps/web`               | React/Vite application, PixiJS tabletop, local interaction previews |
| `apps/server`            | Fastify, WebSockets, server-side dice, SQLite persistence           |
| `packages/core`          | System-neutral validated commands, table state, dice primitives     |
| `packages/module-sdk`    | Module manifests, versioned data and content contracts              |
| `systems/cyberpunk-red`  | Independent Cyberpunk RED module scaffold                           |
| `systems/kids-on-bikes`  | Independent Kids on Bikes module scaffold                           |
| `systems/kids-on-brooms` | Independent Kids on Brooms module scaffold                          |

The server serializes mutations and commits before sending updates. Commands have IDs for retry deduplication over the last 10,000 internal revisions; clients do not automatically replay commands after reconnecting. Every HTTP table response, initial/reconnect snapshot, mutation update, and retry response uses a per-member projection. Global revision counters stay on the server. Client views use a content fingerprint computed only from visible fields, and unchanged views are not broadcast when someone else makes a private roll.

Dragging and unfinished strokes are local previews; committed changes synchronize. This first protocol sends complete projected snapshots and is deliberately small. It is not an offline-first or CRDT implementation. Table schema version 6 includes note documents and persistent per-object/per-note edit versions. Live protocol **16** requires an exact version at the WebSocket handshake and on every snapshot, retaining scene context/live names and adding requester-only command confirmations and member-scoped scene-history cursors. Client action frames are `{ context: { campaignId, sceneId, generation }, command }`; the context must match the current campaign and active scene before authorization, deduplication, or mutation. The generation is the public campaign metadata version, not a private-activity/global revision clock. Switching away and back invalidates older actions even when the scene ID is the same. Invalid/stale context never consumes a receipt; stale actions return an error and a fresh filtered snapshot, without automatic replay. **Reload older browser tabs after this protocol upgrade**; context-free commands are rejected. Version 1/2/3/4/5 saves upgrade automatically, preserving scene content, internal revisions, command receipts, version 2 ownership, and version 3 private roll visibility. Older rolls remain public; ownerless legacy objects stay GM-controlled. Version 1/2/3 saves gain an empty notes collection; version 4/5 notes remain intact. Objects from schemas 1–4 start at edit version 1; schema-5 object versions stay intact. Legacy tokens gain radius 24. Unsupported/incomplete saves and ambiguous object IDs fail validation. Reload older browser tabs after upgrading.

Roll retention is separate for the public audience and each private roller: the latest 100 results per audience, at most 1,100 live records overall. Private rolling never evicts public history or another player's private results. Old results in a full audience drop off; archive them manually before they leave live history if you want to retain them. At the overall cap, a new audience must wait until existing live results are archived/deleted. Archives use separate rows and paged reads, hold at most 10,000 results per campaign, and never enter live snapshots. Existing drawing/token/note limits also remain in force; complete snapshots and large-scene performance work remain queued.

SQLite uses Node 24's built-in `node:sqlite` and prepared SQL, behind a validated store boundary. Campaign storage schema 3 separates campaign-wide notes, rolls, and internal revisions from each scene's drawings/tokens. Campaigns have versioned names/descriptions, one active scene, an exact system package version, and exact content-pack pins. Commands have separate receipt namespaces per campaign; scene changes and competing saves reject stale revisions. Limits are 100 campaigns per server and 100 scenes per campaign.

On first startup after this upgrade, the former singleton table and receipts convert atomically to **The gathering place**, preserving the scene, ownership, notes, rolls, edit versions, and receipts. Access identities/sessions/invitations remain intact. Legacy saves had no package version metadata, so this one-time conversion pins the currently installed version of their selected system. Future loads require matching installed system/content-pack versions; missing or incompatible pins fail explicitly instead of silently upgrading or importing arbitrary code. No content packs are shipped yet. This is a one-way storage upgrade: older builds require a pre-upgrade database backup; downgrade and automated package migrations remain unimplemented. The persisted table schema is 6; live transport is protocol 16.

Access storage schema 1 maps the previous `main` scope to the default campaign UUID. Existing user IDs, names, roles, session/invitation hashes, expiries, invitation IDs, and recovery targets are preserved. Public access contracts now carry a UUID in `tableId`; reload older browser tabs after upgrading. Membership, GM management, invitations, recovery, removal, and credential rotation are scoped to a campaign. A signed-in identity can join an additional invited campaign using `POST /api/access/join` with `keepIdentity: true`; names alone never claim a membership. Anonymous invitation joins still create a new identity, while return codes restore their selected identity. Successful joins and campaign selections replace only the requesting browser session and close its old sockets. Other profiles’ sessions stay in their existing campaigns. The table HTTP/live endpoints resolve their campaign from the session, enforce any supplied `campaignId` query precondition, and never use a client-supplied campaign to choose unauthorized state.

The running server shares one SQLite connection between campaign, access, module-document, and roll-archive stores. Synchronous service transactions can combine campaign/scene creation with access-scope/GM-membership creation atomically; nested store writes use savepoints. Campaign creation uses this boundary to commit its initial scene, access scope, and host membership together. Each live socket is bound to its original credential/campaign/active scene; commands, ownership recipients, receipts, participant counts, and snapshots stay in that campaign. Scene activation pushes fresh context and active-scene data to that campaign without dropping its note drafts. Every mutation checks membership, context, state, and receipts in one SQLite transaction and sends updates after commit. Context includes a public generation, so delayed frames are rejected on old or newly opened connections, including away-and-back scene cycles. Creating an offstage scene and private note/roll activity do not advance that generation or send offstage metadata to players.

This avoids a native package build for self-hosters; normalized campaign/document records currently use explicit prepared SQL. The Node 24 SQLite API may emit an experimental warning.

Modules are trusted installed code, not a sandbox. Each has shared, client, and server entry points and an independent version. Content packs provide stable definition IDs; owned instances carry their own mutable state. Published game data will be added from user-provided sources with edition/page references. Shared Kids-system code should be extracted only after the actual implementations demonstrate common behavior.

## Canvas decision — 2026-11-04

**Keep PixiJS as the live battlefield renderer.** Build the queued drawing/selection tools around Tableloom's validated, owned, versioned scene objects and server commands. Excalidraw is a credible optional map-preparation editor for later asset work; it is not being embedded into the live table in this increment. This preserves the intended quick whiteboard experience as a product goal, rather than treating the current two drawing tools as finished.

The comparison used the installed **PixiJS 8.22.0** and an isolated **`@excalidraw/excalidraw` 0.18.1** spike with the same React 19.3.1/Vite 6.4.5 versions as the app. The package registry's stable version and React peer range were checked on this date; Excalidraw's and PixiJS's installed package metadata both report MIT licensing. The spike ran outside this repository with synthetic shapes, locally copied fonts, two embedded editor instances, and explicit host-side snapshot buttons. It had no campaign access, WebSocket transport, or permission implementation. Its strict TypeScript check and production build passed; the repository's complete `npm run check` also passed with **110 tests**.

**Observed integration work:** A changed independently until host code explicitly copied its scene to B. Native element IDs and the editor's element/version/history model differ from our UUID-based command model. Supporting the full editor would require a bounded schema/ID/binding adapter, canonical-vs-preview reconciliation, batching for multi-element edits, rejection/undo handling, and authorized asset storage. An Excalidraw-plus-Pixi token overlay is also possible, but adds same-client viewport transforms, hit testing, and pointer/keyboard routing between two canvases. These are engineering tradeoffs inferred from the spike and API/source inspection, not claims that embedding is impossible. Excalidraw's `customData` and view/lock affordances would be UI metadata, never the authority for owner or GM access. [Pinned embedding/types contract](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/types.ts).

Its complete output, including optional chunks and all copied fonts, was 21,284,884 bytes; fonts accounted for 13,107,068 bytes. The existing Tableloom output was 973,861 bytes total, with an approximately 678 kB main entry. FPS, mobile behavior, large-scene rendering, and production collaborative-editor integration were not benchmarked. The disposable harness was not retained as a maintained app test suite.

Keep local gesture/camera/selection previews separate from committed server state. The current PixiJS canvas rebuilds its display children on updates; retained rendering/performance work remains in its existing queue item. Revisit this choice if playtesting shows drawing-tool development is the bottleneck or an isolated map editor can meet the command/asset constraints at lower cost. The comparison does not add playable sheets, native Excalidraw files, imports, or new live tools.

## Concurrent scene edits and upgrades

Tokens and drawings now carry an independent positive edit `version`. New objects start at 1, assigned by the server; creation rejects supplied owner/version fields. History restoration keeps the original ID/owner and uses a higher version, never version 1. Ordinary creation cannot reuse an ID already reserved in that campaign. Every accepted token/drawing move, resize, or object ownership transfer advances that object's version. `token.move`, `object.delete`, and `object.assign` require `expectedVersion`; `tokens.move` requires a captured version and destination for every token; the server checks current permissions and the expected version before changing anything. Transfers also retain the existing expected-owner and verified-recipient checks. Drawings support rigid translation of every saved point. Translation, resizing, and ownership transfer advance their versions; arbitrary geometry/style editing remains queued.

If two people move the same token from version 1, one succeeds and the other receives a correlated rejection and the latest filtered scene. An old delete cannot remove a newly moved/transferred object; an old transfer cannot overwrite a newer move/transfer. Moving away and back still changes the version, so an old drag remains stale even at identical coordinates. An absent object cannot be moved; undo restoration advances its version and invalidates older ordinary edits. Edits on distinct objects and unrelated private note/roll activity do not invalidate each other's versions. Exact confirmed-request retries still use their sender/payload-bound receipt before mutation, so they acknowledge the original commit without applying it twice.

The canvas captures a token's version when dragging begins and sends it on release; it does not replace that captured version with a remote update. Simple selection without movement sends no edit. Sidebar/eraser deletes use the displayed version. Ownership review captures the object's version too, and a remote move disables the stale confirmation. Rejections keep authoritative state and receipts unchanged and report the conflict through recent-action feedback; users review the current scene and explicitly try again. There are no object locks, automatic merges/replays, or conflict-resolution dialogs. Future geometry/style edits must also advance object versions.

**Upgrade:** live protocol 16 requires version preconditions; table schema 6 requires object versions and explicit token radius. Campaign storage 1/2 upgrades atomically to schema 3 on startup, validating every campaign and active/offstage scene together. Schema-1 objects gain version 1; schema-2 object versions stay intact. Every legacy token gains radius 24, retaining its prior appearance. Existing drawings, content/owners, notes/private rolls, note/document edit versions, campaign metadata/generations, scene IDs, command receipts/bindings, access credentials, module documents, and archives are preserved. Current schema-3 records must already have valid versions and sizes; missing values are never silently reseeded. Standalone table schemas 1–5 migrate through validated legacy paths. Malformed/unsupported data or a failed write rolls the campaign upgrade back, including its marker.

This is a one-way storage upgrade: keep a pre-upgrade database backup if you need to run an older build; automatic downgrade/restore remains queued. Older builds reject campaign storage 3, protecting saved sizes and version counters from accidental resets. **Reload older browser tabs before playing with the upgraded server.** No published game rules or module catalog content are involved in this migration.

## Durable scene-edit undo/redo

**Undo last edit** and **Redo last edit** above the battlefield act on your own confirmed individual/group token/drawing resizes, token moves, atomic token/drawing/mixed-group moves, and token/drawing creations and individual/group deletions in the active campaign/scene. The GM can undo their own edits of objects they still control; they cannot undo another member’s history. Undo/redo survive disconnects, browser reloads, and server restarts. Buttons pause while a supported scene edit awaits confirmation or the connection is unavailable. Existing recent-action feedback confirms or rejects each request. No local/offline undo or automatic replay occurs.

Live protocol **16** sends only the requesting member’s next undo/redo cursors: `{ id, version, objectId, objectCount, action, objectType, name, available }`, or `null`. Other members’ history IDs and stored inverse geometry/owners never enter these history fields. `scene.undo`/`scene.redo` still accept only a history ID and expected history version within the exact live context. The server resolves the inverse, rechecks persisted membership/current permissions and the expected object version, and atomically commits scene state, history, ID reservations, receipt, and request binding. Exact retries confirm without applying twice.

Create → move → delete can be undone and redone as one causal sequence, including interleaved objects. Restoring a deleted object keeps its UUID, saved geometry/style/name, and original owner; it never assigns ownership to the requesting GM. Removed owners remain recorded and their objects remain GM-controlled. Restores append to the current drawing/token render order and obey the existing 200-token/2,000-drawing scene limits. Each removal reserves the next version in history; each restore/move advances it again, so old drags/deletes/transfers remain stale. Only uninterrupted edits by the same member are rebased onto neighboring cursors. Intervening remote/ownership edits break the chain, even if coordinates return to the same values. Blocked edges cannot skip to older unrelated edits; no skip/clear-history control exists yet. A new ordinary supported scene edit discards only that member’s redo suffix in that scene. Unrelated private note/roll activity leaves it alone.

**Object IDs are reserved per campaign.** A new token, drawing, or note must have a fresh UUID, including after deletion, undoing creation, changing scenes, or history eviction. This prevents an old version-checked command from matching a replacement object's reset version. Undo/redo are the restoration path for an existing ID. Content-free reservation storage schema **1** seeds existing tokens/drawings in every active/offstage scene, campaign notes, and retained legacy move targets. Reservations survive history pruning/restart and are capped at **250,000 distinct IDs per campaign**; at the cap, restores/edits still work, while new objects require another campaign. There is no reclamation tool. IDs forgotten by older builds before this upgrade cannot be reconstructed; reload older tabs before continuing play.

Scene-history storage schema **8** validates and upgrades schema-1 moves, schema-2 scene entries, schema-3 token groups, schema-4 mixed translations, schema-5 group deletions, schema-6 drawing resizes, and schema-7 token sizes atomically, preserving IDs, sequence, state, cursor versions, per-object expected versions/causal links, and inverse payloads. Each history entry carries a bounded target list so overlapping groups can rebase only their own causal targets. New drawing/mixed translations store original geometry plus a shared offset on the server; undo restores original coordinates exactly, and redo repeats the original addition, preventing floating-point round-trip drift. The same transaction initializes ID reservations; invalid/future/incomplete data or failed writes roll it back. Current table schema is **6** and campaign storage is **3**. Existing moves remain undoable; earlier creation/deletion history is not invented. Retention is at most **100 edits per member per scene**, **10,000 per campaign**, and **32 MiB of serialized inverse payloads and target links per campaign**, pruning oldest prefixes. Links to expired predecessors are ignored; they cannot restore pruned edits. The byte cap measures payloads and target lists, not SQLite file/index size. These are bounded editing stacks, not an audit log, trash, or backup. Group deletion stores server-chosen owned-object snapshots and restores the whole group with higher versions, preserving exact geometry/styles/names/owners. Ownership transfers, notes, rolls, and settings have no undo. Reload older tabs for protocol 16; older history builds reject schema 8, and downgrade/backup tooling remains queued.

## Object multi-selection and atomic movement

With **Select & move objects**, click a token you control or the edge/line of a drawing you control. **Shift-click** adds/removes objects. Stroke hit testing follows segments between sampled points; room interiors stay available for box selection. Tokens remain above drawings when picking. Drag empty space to select editable objects: token centers and complete drawing bounds must fall inside the box. Shift-drag adds to the selection. This lets you select a token inside a large room without accidentally moving the room. Drag any selected token or drawing edge/line to move the selection, or use **Clear selection**. Selection is local, capped at **100 objects**, and makes no saved changes by itself. Oversized selections report the limit and keep the prior selection. Missing/newly uneditable objects leave local selection. Campaign/scene changes or reload clear selection; disconnect/tool changes cancel gestures.

A drag captures every selected object’s starting geometry and version and preserves spacing, shape, and pointer offset. At world bounds, all saved geometry stops together. Wheel zoom pauses during gestures. Token-only drags retain `token.move`/`tokens.move`; drawing or mixed drags use strict **`objects.move`**, containing **1–100 distinct IDs**, each expected version, and a single nonzero translation offset. The server accepts no caller-supplied replacement geometry, object kinds, styles, or owners. It verifies every target’s existence, type, current permission/version, and every resulting coordinate before applying anything. Accepted movement advances each object’s version but saves **one campaign revision, receipt, binding, and history entry**. One stale, deleted, unauthorized, duplicate, invalid, or out-of-bounds target rejects the whole move, refreshes the caller’s filtered view, and never partially applies or automatically replays it.

Undo/redo also validate the entire selection. Per-target causal links support overlapping token, drawing, and mixed moves alongside earlier individual create/move/delete entries. One remote edit or ownership transfer blocks the entire affected history edge. Geometry in new translation history stays on the server; only the first target ID, count, type (`token`, `drawing`, or `mixed`), name, and action reach that member’s history cursor. Original coordinates make decimal-coordinate undo exact; redo computes from those same originals. Original geometry/target lists count toward the existing 32-MiB campaign history cap. This does not add persistent named groups, rotation, or full keyboard/touch selection. Individual and group resizing are described below. Optional local grid snapping is described below. Large-scene/FPS measurement remains queued.

## Atomic group deletion and restoration

After selecting objects, choose **Delete selection…**. The review lists the captured token names and drawing kinds, with Cancel focused first. Confirming deletes exactly that reviewed set for everyone in the active scene. If a target moves, disappears, changes owner/type, or becomes uneditable during review, confirmation is disabled; cancel and review again. The set never silently shrinks or refreshes its captured versions. Related pending edits and disconnects also disable deletion. A race after confirmation still receives an all-or-nothing server rejection and the latest view. The existing recent-action foldout reports confirmation/rejection/unconfirmed delivery; no deletion is replayed automatically.

Protocol-16 **`objects.delete`** accepts **1–100 unique object IDs and expected versions**, with no caller-supplied snapshots or owners. The server verifies all current permissions, existence, and versions before removing anything, and commits one revision/receipt/binding/history entry. Invalid, duplicate, missing, stale, or unauthorized targets reject the entire set. Sidebar and eraser actions retain their single-object behavior.

Undo restores every saved object in that deletion together, keeping IDs, original owners (including removed owners under GM control), names, styles, and exact geometry. Each removal/restore advances per-target versions; stale moves/deletes/transfers cannot act on restored objects. Redo removes the restored set only if every target remains permitted and unchanged. Restoration requires all target IDs to remain absent and enough capacity for the **entire** set under the scene’s 200-token/2,000-drawing limits. No partial restore occurs. Restores append in each object type’s current render order and do not reselect objects locally. The normal 100-edit/member/scene, 10,000-edit/campaign, and 32-MiB history limits apply; deletion history can expire, so Undo is not trash or backup storage. No restore/export browser or history-skip control is added.

## Drawing resize

Select one editable room or freehand drawing with **Select & move objects**, then drag a square corner handle. The opposite corner stays fixed; the drawing scales independently on each axis without changing its color, kind, owner, UUID, point order, or line thickness. Turning on **Snap to grid** snaps the dragged corner to grid intersections while retaining the fixed corner. Pointer offset and snap mode are captured at drag start; a click or movement under three screen pixels sends no edit. Corners stop at world bounds and a minimum width/height of one world unit; they cannot flip or collapse. Drawings with zero width or height have no resize handles. Tokens have a separate size dialog described below; multi-object selections use the percentage-based group resize dialog below.

Protocol-16 **`drawing.resize`** accepts only a drawing UUID, captured expected version, and strict finite target bounds within ±10,000. The server rechecks current ownership/existence/version, transforms its saved points into those bounds, validates all resulting geometry, and commits one revision/receipt/binding/history entry. It accepts no caller-supplied replacement points, styles, owners, or assigned object versions. Unchanged/degenerate/invalid bounds, missing or unauthorized drawings, and stale drags fail without saved changes or automatic replay. Axes whose bounds stay unchanged preserve their points exactly.

History schema **8** stores bounded exact before/after point arrays on the server. Undo/redo copy those points instead of reversing a floating-point transform, advance object/history versions, and participate in existing create/move/delete/group causal chains. Only the requesting member’s next cursor exposes the `resize` action; stored geometry and other members’ cursors stay out of history fields. Ordinary resize and inverse commits share existing transaction, retry, retention, permission, and conflict guards. Histories from schemas 1–7 upgrade atomically with preserved entries/cursors/causal links; invalid/future/incomplete data or failed marker writes roll back. Current markers are table schema **6**, campaign storage **3**, and object reservations **1**. **Reload older tabs before playing; older history builds reject schema 8.** Rotation/aspect locks, individual handles for flat strokes, keyboard/touch resizing, and downgrade tooling remain queued.

## Token size

Select one editable token and choose **Resize token…**. Enter a diameter of **8–600 canvas units**; decimals are supported. The default diameter is **48**, and a grid cell is **60** units across. These are neutral canvas dimensions. Resizing keeps the token’s center, UUID, name, color, owner, and circular shape. Its circle, selection ring, initial, name placement, and click/eraser hit area follow the saved size. Movement, box selection, and grid snapping continue to use its center. The center remains bounded to ±10,000; the rendered circle can extend beyond that edge. Grid snapping does not force a token diameter.

The dialog captures the token/version/owner when opened and preserves its draft. Any move, resize, transfer, deletion, or loss of edit access disables submission; cancel and reopen to review the current token. Unchanged/invalid diameters, pending edits, and disconnects also disable submission. Confirmed updates appear in recent actions. Protocol-16 **`token.resize`** accepts only the token ID, captured expected version, and a finite radius of **4–300**. The server rechecks current permission/existence/version, rejects unchanged sizes, and commits one object-version increment, scene revision, history entry, receipt, and binding. Creation always assigns radius 24 and rejects supplied size/owner/version fields. No automatic retry/replay occurs.

Table schema **6** and campaign storage **3** make size explicit. Campaign storage 1/2 upgrades all active/offstage/other-campaign tokens to their previous fixed radius 24; version counters, geometry, metadata, private content, access, receipts, bindings, and independent documents/archives are preserved. Invalid hidden data or failed marker writes roll back the campaign upgrade. History schema **8** upgrades old scalar/group token snapshots too, so deleted tokens restore at their original fixed size. It retains IDs/cursors/causal links and stores exact before/after radius for new size edits; undo/redo advance versions and participate in existing move/create/delete/group chains. History upgrades validate old capabilities and roll back their own writes on failure. Current missing sizes fail closed instead of guessing. Object reservations remain schema **1**. **Reload older tabs; older servers reject the new campaign/history markers.** Token drag handles, diameter presets, and keyboard/touch refinements remain queued.

## Atomic group resize

Select **2–100 editable objects** and choose **Resize selection…**. Enter a scale from **1–10,000%**: 50% halves sizes/spacing and 200% doubles them. The dialog lists the frozen targets, shows before/after bounds and a local geometry preview, and keeps the draft if a remote edit arrives. Any selected object moving, resizing, changing owner, disappearing, or losing edit access disables the entire confirmation; cancel and review again. The set never silently shrinks. Unchanged 100%, invalid/excessive scales, pending edits, and disconnects also disable submission. The scrollable review keeps long target lists bounded. Recent actions confirm/reject the edit for the requester.

Protocol-16 **`objects.resize`** contains only **2–100 distinct object IDs/expected versions** and a finite non-unit scale factor of **0.01–100**. The server chooses the center of the selection’s combined bounds using token circular footprints and every drawing point. It uniformly scales token positions/radii and drawing points around that center, preserving circles, proportions, relative spacing, UUIDs, point order, names, colors, owners, and line thickness. All current permissions/versions/existence, token radii (4–300), and saved center/point world bounds (±10,000) validate before any mutation. Flat strokes can scale as part of a group without division by zero; a wholly unchanged coincident selection rejects. No replacement geometry, caller-chosen center, style, or owner is accepted. A single invalid target rejects everything; sizes are never silently clamped. Every included object advances its version, with one scene revision/receipt/binding/history entry. Grid snapping does not quantize group scaling; rounding individual targets would distort the group. Token footprints can extend beyond the world edge under the existing center-bound rule.

History schema **8** stores exact server-chosen before/after positions/radii/points for the whole group, never inverse division. Undo/redo recheck every target’s current kind/permission/version and restore all geometry together with higher versions. Per-target links support overlapping move/size/create/delete/group chains; intervening edits by another member block the entire affected edge. Exact retries do not repeat either resize or inverse; failures roll back state, history, receipts, and bindings. Only the requester’s aggregate `resize` cursor enters history fields; saved geometry stays on the server. Existing 100-edit/member/scene, 10,000-edit/campaign, and 32-MiB inverse/target limits apply. Schemas 1–7 upgrade atomically with preserved cursors/links/inverses and saved token sizes; invalid/future/incomplete data or failed marker writes roll back. Table **6**, campaign storage **3**, and object reservations **1** stay unchanged. **Reload older tabs; older history builds reject schema 8.** This completes the initial resize/snapping/history checklist. Drag handles for groups/tokens, arbitrary anchor choice, nonuniform group scaling, rotation, and broader keyboard/touch interaction remain future refinements.

## Private map asset library

Campaign GMs can open **Map assets** in the left rail, choose a PNG, name it, and **Upload privately**. The library shows usage, metadata, a selected image preview, and paged results (**Refresh library** / **Load more assets**). Only campaign GMs can list, upload, download, or remove these images. Players receive neither library metadata/IDs nor bytes, even with a guessed content URL. Every operation checks current persisted campaign membership/role; changing the active campaign invalidates the old URL scope. Uploads remain private to that campaign’s GMs across reload/restart. **Battlefield placement/reveal is not implemented yet**; images never enter scene state, live snapshots, history, campaign/scene lists, or visible revision fingerprints.

The first accepted format is **static, non-interlaced, 8-bit RGB/RGBA PNG**, at most **5 MiB uploaded**, **8,192 pixels per side**, and **16,777,216 total pixels**. The server validates the complete signature/chunk structure/order, checksums, dimensions/mode, bounded decompression length and consumed compressed bytes, and per-row filter codes. Truncated files, trailing/extra compressed data, invalid CRCs/chunk types, animation, indexed/grayscale/interlaced/16-bit PNG, color-key transparency, JPEG, SVG, and other formats reject without storing anything. Export unsupported sources to RGB/RGBA PNG for now. Accepted images retain their compressed pixel data; ancillary metadata (including text, physical-resolution information and color profiles) is removed. This can affect profile-managed color appearance. Decoding validation is bounded to the permitted pixel rows (at most 64 MiB plus filter bytes), runs synchronously, and is GM-only; image-processing performance/thumbnail work remains queued.

Independent **asset storage schema 1** stores immutable server-assigned UUIDs, names, dimensions, byte lengths, creation times, integrity hashes, and canonical PNG bytes in a separate SQLite table. Binary BLOBs and metadata commit together, with no separate asset directory or orphan-file cleanup. Libraries allow **200 images and 100 MiB of stored normalized image bytes per campaign**. Upload budgets and quotas validate before insertion in the transaction; failed writes leave the library unchanged. Removal permanently deletes the private upload and frees its live quota, with an explicit review and no Undo/trash. There are currently no scene references; asset-use guards must precede placement. Deleted SQLite pages may remain in the database file until future maintenance/compaction; the quota measures live PNG bytes, not file/index/WAL size. Consistent backup/restore remains queued and must include the database’s binary assets.

The authenticated API root is `/api/campaigns/:campaignId/assets`:

| Route | Contract |
| --- | --- |
| `GET /` | GM-only metadata page; optional UUID `after` and `limit` 1–50 (default 20), with `nextCursor`, count, and stored byte usage. No binary data in lists. |
| `POST /?name=...` | GM-only same-origin upload, raw `Content-Type: image/png` body, trimmed 1–120-character logical name, response 201 with validated metadata. Names are labels, never paths. Authentication/GM checks occur before reading the bounded upload body and are rechecked before storage. |
| `GET /:id/content` | Current-campaign GM-only PNG response with integrity/metadata checks, `no-store`, `nosniff`, generated inline filename, and restrictive content policy. Players/foreign-campaign IDs cannot retrieve content. |
| `POST /:id/delete` | GM-only same-origin permanent removal; strict empty JSON object body. Unknown/already-removed assets are unavailable. |

The browser does not automatically replay uploads/removals. Upload requests have no durable HTTP retry receipts; a lost response may hide a successful save, so refresh before manually retrying. Library requests are scoped to the viewer/campaign; pending reads/uploads abort on dialog teardown, although an already committed request remains saved. No automatic cross-GM library refresh, deduplication, renaming, public links, remote URL imports, placement, migration/downgrade tooling, or asset recovery exists yet. Table **6**, campaign storage **3**, live protocol **16**, scene history **8**, and object reservations **1** remain unchanged; all game-system packages remain independent scaffolds.

## Local snap-to-grid

**Snap to grid** on the battlefield is optional and starts **off** for each table context. It is a browser interaction preference, not a shared campaign setting or game-system rule. Turning it on does not move saved objects. New token centers snap to cell centers on the existing **60-unit square grid**; new room corners snap to grid intersections. Freehand drawing remains freehand. Room gestures with zero width or height create no object. The token-name panel sits below the snap control so both remain usable.

For selected-object movement, the grabbed token’s center snaps to cell centers, or a grabbed drawing’s upper-left geometry bound snaps to grid lines. One common translation moves the entire selection, preserving shapes and relative spacing; other members of an off-grid group are not independently realigned. The mode and anchor are captured at drag start alongside the existing positions/versions. Clicks and movement below **three screen pixels**, at any zoom, remain selection-only and create no history. Snapped movement chooses a grid-compatible position that keeps every point inside the world bounds. If an almost world-sized off-grid group has no compatible position on an axis, that axis stays unchanged; turn snapping off for free movement.

The rendered grid follows the viewport/camera at the same zero origin throughout the existing world bounds, including panning beyond its former fixed patch. Visible line generation is bounded, and a resize observer keeps the renderer/grid aligned with the battlefield after layout changes. Snapped coordinates use the existing authoritative creation/movement commands and history, with the same ownership/version/context checks, atomic groups, exact undo/redo, and no automatic replay. Clients can still submit valid free coordinates; the server does not force a grid. Current versions are live protocol **16**, table **6**, campaign storage **3**, history **8**, and object reservations **1**. Snap choice is in memory and resets on context change/reload; persisted/shared grid settings, configurable spacing/origin, hex grids, and keyboard/touch refinements remain queued.

## Connection recovery

The browser checks the server's protocol before each live connection and waits for a validated fresh snapshot before enabling changes. Every attempt has a ten-second deadline, covering the health request, handshake, and first snapshot. Transient failures retry with jittered exponential delays (roughly 0.75–1, then 1.5–2, 3–4, 6–8, and up to 15 seconds); server overload waits at least three seconds. Old connection callbacks cannot replace a newer view or restart a stopped connection.

During an ordinary outage, the last validated table remains visible with editing disabled and participant count reset. In-memory note drafts stay editable locally. Reconnecting restores server state; a conflicting saved note keeps its local draft and blocks stale save/delete until the user explicitly reloads the latest version. Credential loss clears the cached view, and identity/campaign changes clear drafts as before. Drafts do not survive a page reload, and no offline changes are queued or replayed. A change sent just before an interruption may have saved: review the reconnected table before retrying. Command confirmations distinguish pending, confirmed, rejected, and unconfirmed changes as described below.

Live clients must supply `protocolVersion=16` on `/api/live` (alongside the expected `campaignId`). After origin/authentication/campaign checks, missing/malformed/other versions receive HTTP 426 with the supported version and no campaign state. Snapshots include `protocolVersion: 16`; table schema 6 adds scene-object versions, preserving existing content through the migration below. **Reload browser tabs from older builds.** A health/snapshot version mismatch, unreadable snapshot, or protocol/policy/oversize close stops automatic retries, disables changes, and offers **Reload page**. Reloading discards local drafts; copy needed text first. A foreign-campaign snapshot also clears the cached view.

The browser refuses a new action if its serialized UTF-8 frame plus unsent WebSocket bytes would exceed 256 KiB, reporting that the change was not sent. It never builds an application replay queue. The server retains its 256 KiB incoming-frame limit, command rate limit, and 30-second ping/reauthentication checks. Its output is now serialized and bounded as described below. Scene edits use the version checks below; offline play is not implemented.

## Command confirmations

The foldout above the battlefield shows recent actions in this browser as **Waiting for confirmation**, **Confirmed**, **Rejected**, or **Not confirmed**. The server sends `{ type: "ack", commandId }` only to the requesting connection after the state, deduplication receipt, and request binding commit together. Rejections include the caller's `commandId` on the existing error frame and reload that caller's filtered view. Invalid/unparseable frames have only a general error. No results, payloads, private counters, or other members' request IDs are broadcast as confirmations. The caller's supplied ID is echoed even if it happens to be reused in a different campaign; that does not expose that campaign's records.

Each new committed receipt has a separate command-binding schema 1 row containing its authenticated sender and a SHA-256 digest of the validated frame. Exact retries by the same sender/context/payload can be confirmed without executing again. Changed-payload/other-sender reuse and legacy unbound receipts receive a generic rejection and current filtered view, without changing state or claiming the requested action succeeded. Bindings survive restart and cascade away when the existing receipt expires (the normal 10,000-revision window). Failed binding writes roll back the state and receipt too. No old receipt is assigned an invented sender or payload.

At most 64 commands await confirmation per connection. Each has a ten-second deadline; timeout/disconnect/incompatible-connection failures mark outstanding actions **Not confirmed** and never replay them. A late or unknown acknowledgement cannot confirm a newer request, and ordinary snapshots do not count as acknowledgements. Review the current state before explicitly trying an unconfirmed action again. This is an in-memory delivery view, not durable request recovery: reload/identity/campaign changes clear it. The browser retains pending entries and the latest 20 finished statuses (the foldout shows the latest 20 overall), with action names and target IDs internally, not full command contents.

Note saves/deletes also show their own delivery feedback and disable duplicate save/delete while awaiting confirmation. You may keep editing a draft during that wait. If a concurrent note save wins, the rejected save retains its draft and the refreshed note version activates the existing conflict/reload control. Confirmed means that specific change committed; another editor may change the state afterward. HTTP document/history/campaign mutations keep their existing HTTP responses and do not use these WebSocket confirmations. Automatic retry, post-reconnect receipt lookup, and durable outboxes remain unavailable.

## Server output and slow connections

Each live connection has one active WebSocket write. Acknowledgements and errors wait in a FIFO bounded to 64 frames and 64 KiB of UTF-8 JSON, including an active control frame. Overflow closes that connection with code 1013; already committed changes remain saved and unreceived confirmations remain uncertain. Incoming commands are ignored once the socket begins closing. One slow client does not create a backlog for other connections.

Snapshot and presence requests use dirty flags rather than storing serialized messages or old table objects. Multiple waiting requests collapse to one fresh snapshot and one current participant count; forced refreshes remain forced. After the active write completes, command results drain first, then the latest requested snapshot, then presence. A client may skip intermediate states, while still receiving its queued command results. Snapshots are rebuilt from current SQLite state and current membership/role when they actually drain, retaining the existing visible-data fingerprint suppression. A queued request cannot publish a note that was retracted before its snapshot was built. Membership is rechecked before every write; access closure drops all waiting work immediately.

A write that does not complete within ten seconds closes with 1013. Preparation/write failures close with 1011; access failures use 4001. Closed channels discard queued results/flags, ignore late callbacks, and force termination after one second if the close handshake stalls. Successful close/shutdown cancels their timers. The browser's existing reconnect/backoff and unconfirmed-delivery behavior apply; the current formats are live protocol 16/table schema 6.

This bounds waiting output to one active frame, bounded control metadata, and two coalesced flags. There is no new small fixed snapshot-size cap: existing valid scenes larger than the former 4 MiB buffered-byte threshold remain supported as one active write. A full snapshot can still be large within the drawing/token/note/roll limits, and serialization/validation work is synchronous. This is queue control, not a full process-memory/performance limit; snapshot chunking/deltas and large-scene measurement remain queued. Tests model stalled write completion deterministically; a production slow-network load test is still future work.

## Module document API

Module-backed documents are separate normalized rows, never included in table snapshots or campaign/scene lists. The current modules validate only provisional `{ name, notes }` data with document schema version 1; they do not implement published character sheets or game rules. Existing plain-text notes stay separate and are not converted. A browser sheet editor and module actions remain queued.

These cookie-authenticated endpoints require the URL campaign to match the session's active campaign. Select the campaign first; supplying an ID never grants membership. Mutations require the server origin. All responses use `Cache-Control: no-store`.

| Endpoint (under `/api/campaigns/:campaignId/documents`) | Behavior |
| --- | --- |
| `GET /` | Visible metadata only, ordered by UUID; optional `after` UUID and `limit` (1–50, default 25). Returns `{ documents, next }`, with `next: null` at the end. |
| `POST /` | Accept `{ title, system: { id, version }, visibility?, data? }`. System pin must exactly match the campaign. Server assigns UUID, owner, schema version, and edit version 1. Missing data uses the installed module factory; visibility defaults to private. |
| `GET /:id` | Fetch one authorized document and validate its stored JSON against the pinned module's current schema. |
| `POST /:id` | Owner/GM only; accept `{ expectedVersion, title, visibility, data }`. Advance the edit version; stale versions return 409. |
| `POST /:id/delete` | Owner/GM only; accept `{ expectedVersion }` and permanently delete. |
| `POST /:id/migrate` | GM only; accept `{ expectedVersion }` and explicitly run the installed module's consecutive schema steps atomically. |

`visibility: "gm"` grants read access to the owner and campaign GMs; `"public"` grants read access to campaign members. Only owner/GM can edit/delete. Visibility is filtered in SQL before payload decoding or pagination. Hidden/foreign document IDs receive the same 404 as unknown IDs. Lists do not expose hidden titles, owner IDs, schema versions, bodies, or totals. Removed members lose access while the GM retains their documents. Private document activity never advances the table revision, campaign generation, or unrelated members' view fingerprints. Documents have no live change events yet: clients must refetch to see edits or access changes. Previously shared content cannot be recalled.

Each campaign is limited to 500 module documents with 120-character titles. Each payload is bounded to 64 KiB of serialized UTF-8 JSON, 10,000 value nodes, and nesting depth 20. Values must be finite JSON; cycles, sparse arrays, accessors, class instances, and silent serialization losses are rejected. Module input and migration outputs pass both JSON bounds and module schema validation. Ownership and package pins are immutable through these endpoints; no ownership-transfer or definition/content-pack catalog API is included.

Document storage schema 1 is independent of campaign storage schema 3, access storage schema 1, and table schema 6/live protocol 16. Every row records its exact system package pin, document `schemaVersion`, and optimistic edit `version`. Server-only module entry points can supply validated consecutive `from → to` schema migrations through `@tableloom/module-sdk/server`. Older document schemas remain listable but cannot be opened/edited until a GM explicitly migrates; absent steps, future schemas, invalid outputs, stale versions, and failed writes leave the row unchanged. Migration hooks are trusted installed code and do not enter the browser. The three scaffolds have no historical schema steps yet; execution is verified with synthetic test fixtures.

This executor handles schema changes within the exact installed package pin; coordinated upgrades to another package version are not implemented. Campaign system/version changes are blocked while incompatible documents exist, including through live `system.set`, so records cannot be stranded silently. Remove those documents or wait for a supported package-upgrade workflow before switching systems. Document APIs have no create retry receipts, history, trash, restore, bulk migration, or sheet UI yet. Roll archive/cleanup controls are available below; broader snapshot-performance work remains queued.

## Roll history and archive

Open **Manage roll history** in **Dice & rolls** to select up to 100 visible results. **Archive selected** moves them out of live history while preserving their exact dice, total, attribution, time, owner, and audience. **Browse archive** reads saved results in pages of 50, with **Next page** and **First page / refresh**. The GM can manage any result; players can archive/delete only their own private rolls. Public results can be removed only by a GM, including public rolls made by a player.

**Delete selected…** opens an explicit review before permanently deleting live or archived results for everyone who could read them. There is no undo/trash. New rolls arriving after selection are not affected; a missing/unavailable selection rejects the entire batch. Refresh/reselect after a stale request. Archives have no automatic retention, restore-to-live, export, chronological search, or live change events yet. Results are paged by UUID, not roll time; archive edits by another member appear after refresh. Archive deletion frees archive capacity; live archive/deletion frees the overall live-history capacity. Removing a member preserves their private archive for the GM. Previously read/downloaded results cannot be recalled.

All endpoints below require a cookie-authenticated active campaign matching the path, validate strict ID-only bodies, enforce the server origin on mutations, and return no-store responses. Hidden/foreign/unknown selected IDs use the same unavailable response. No result contents or global/private history counters are accepted from clients or added to snapshots.

| Endpoint under `/api/campaigns/:campaignId/rolls` | Behavior |
| --- | --- |
| `GET /archive` | Return `{ entries: [{ roll, archivedAt }], next }`, filtered before decoding/paging. Optional `after` UUID and `limit` 1–50 (default 25). No hidden totals. |
| `POST /archive` | Accept `{ ids }` (1–100 unique UUIDs); atomically archive authorized live results and remove them from live state. |
| `POST /delete` | Accept `{ ids }`; permanently remove authorized live results. |
| `POST /archive/delete` | Accept `{ ids }`; permanently remove authorized archived results. |

Roll archive storage schema 1 initializes separately from existing campaign/access/document storage. The current persisted table schema is 6 and live protocol is 16. Archive insertion and live removal share a transaction, including the saved table revision and receipt; failed writes or capacity checks leave both unchanged. Original dice command receipts remain, so a retry cannot recreate a result after archive/cleanup within the normal receipt-retention window. History operations themselves do not have retry receipts: a repeated successful batch receives unavailable rather than replaying. Live removals send fresh recipient-filtered snapshots after commit; archiving someone else's private results does not change your visible fingerprint or campaign generation. Archive deletion never broadcasts a private activity clock. This is manual history management, not a complete audit log or backup procedure.
