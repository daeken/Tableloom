# Tableloom

A self-hosted, web-based virtual tabletop for the systems you actually play. TypeScript throughout, a shared sketchable battlefield, and code-first game modules with custom sheets, rules, and content packs.

**Status:** authenticated tabletop with object permissions, private rolls, and shared/private note documents. Returning-player recovery, member/invitation management, and GM ownership reassignment are available. Campaign management/selection APIs and isolated live rooms are available, with exact package pins and campaign-scoped credentials. The browser now has campaign selection/settings and GM scene controls. Versioned module-backed document storage/APIs, explicit GM schema migrations, and roll-history archive/cleanup controls are available; browser sheets remain queued. This README is the authoritative work queue. Cyberpunk RED, Kids on Bikes, and Kids on Brooms are the initial module targets; their rulebooks have not been supplied and no published mechanics or catalog content are implemented yet.

## Run locally

Requires Node.js 24 and npm. No database service or external account is required.

```sh
npm ci
npm run dev
```

Open http://localhost:5173. On first launch, create the host using the private key in `data/host-key` (or your configured `TABLELOOM_HOST_KEY`). The server prints the file location, never the key itself. Keep this key private: it can also recover the host identity after signing out or losing a session. Existing prototype scene data is retained.

Once signed in, the host can choose **Invite & players**, create a one-use code, and share the table address and code with a friend. The friend enters a name and that code. Use separate browser profiles to test independent identities; ordinary tabs share a browser session. A player cannot create invitations.

Sessions last seven days and survive server restarts. Signing out revokes the session and clears the browser table. The host can select **I'm the host** to recover access with the private key. For a returning player, the GM opens **Invite & players** and chooses **Create return code** beside their existing membership. The player enters that code on the same join screen; their original identity, name, object ownership, private notes, and private rolls are preserved. The name entered on the join screen is used only for new-player invitations. Issuing a new return code replaces that player’s previous unused return code; using it signs out all of their previous sessions. Codes expire after one day and work once. Names alone never recover an identity.

The development server proxies `/api` and the WebSocket to Fastify on port 3001. The browser opens the campaign selected by its session and that campaign’s active scene. New invitations enter their own campaign; host setup/recovery opens the default campaign. Use the campaign name in the header to select/create a campaign, edit its settings as GM, or join another invitation under your existing identity. The campaign and active-scene headings update live. GMs can open **Manage scenes**, create an empty offstage scene, and review **Show scene to everyone** to move the whole campaign to it. Each scene retains its own drawings/tokens; campaign notes and rolls stay available. Save drafts before changing campaigns. In-memory note drafts survive scene changes, while unfinished canvas gestures/selection reset. SQLite data lives in `data/tableloom.sqlite` (ignored by Git).

```sh
npm run check       # strict types, tests, build, production smoke check
npm run build
npm start           # frontend + API on http://127.0.0.1:3001
```

Configuration: `PORT` (default `3001`), `HOST` (default `127.0.0.1`), `DATA_DIR` (default `./data`), optional `TABLELOOM_HOST_KEY` (32–512 characters, otherwise a random key is generated in a private `host-key` file), and optional `PUBLIC_ORIGIN` (the browser-facing HTTP(S) origin, without a path). For an HTTPS reverse proxy, set `PUBLIC_ORIGIN=https://your-table.example`; this enforces the configured origin and enables Secure session cookies without trusting forwarded headers. Development defaults to same-origin HTTP on loopback.

Only authenticated members can fetch or connect to the table. Everyone can draw, create tokens, and roll dice. Players can move/delete their own tokens and delete their own drawings; the GM can edit every object and change the game system. The server assigns ownership to the creator; creation commands reject caller-supplied ownership. Older objects without a recorded owner stay under GM control until assigned. The GM can select **Manage ownership** below the cast list, choose a token/drawing/note and a current member, then review and confirm the transfer. Removed members cannot receive ownership. Assigning an object to the GM keeps it under GM control.

Scene objects are currently public to all table members. Before rolling, choose **Everyone at the table** or **You and the GM**. Private rolls are visible only to the roller and the GM; a GM's private rolls stay with the GM. The history marks private results explicitly. Public is the default, and already-recorded roll visibility cannot be changed. Sign-out/identity changes clear the local roll draft.

The **Notes** panel supports plain-text documents. **New** creates a private note visible to its owner and the GM; GM-owned private notes stay with the GM. Set **Who can read this?** to **Everyone at the table** and save to share a note. Other players can read shared notes; only the owner and GM can edit or delete them. Changing a note back to private removes it from other players' current/future views. Previously shared text may already have been read.

Note edits require **Save changes**. Unsaved drafts stay in memory when switching notes/tabs and through unrelated table updates; save before reloading or signing out. Clean editors follow remote saves. If another editor saves while you have a draft, your draft is retained and stale saves/deletes are blocked until you explicitly reload the latest version. Notes are limited to 100 per campaign, 120 characters per title, and 10,000 characters per body.

The GM can list members and unused codes, revoke codes, and remove players in **Invite & players**. Member/code lists never return saved bearer credentials; a newly issued code is displayed only in its issuing dialog. Removing a player immediately revokes their sessions and return codes. Their existing objects, notes, and rolls remain stored and available to the GM; removal does not reassign or publish them. A fresh invitation creates a different identity, even with the same name. The host cannot be removed. Backing up the private host key still needs a complete backup/recovery procedure. Module-backed documents have a separate API described below; character-sheet UI, rich text, attachments, and version history are not implemented yet.

Note transfers keep the saved content and visibility. A private note requires explicit confirmation before the new owner receives its full saved text and the previous player owner loses access. The GM always retains access. A public note stays readable by the table, but edit/delete rights move to the new owner. Transfers advance the note version, blocking stale edits/deletes; the review screen blocks confirmation if the note changes while being reviewed. Save drafts before transferring. Hidden notes and their local drafts disappear from the previous player’s current view; previously read content cannot be recalled. Dice results keep their original ownership and attribution. Ownership transfers have no dedicated history or undo yet.

## Architecture

| Location                 | Responsibility                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| `apps/web`               | React/Vite application, PixiJS tabletop, local interaction previews |
| `apps/server`            | Fastify, WebSockets, server-side dice, SQLite persistence           |
| `packages/core`          | System-neutral validated commands, table state, dice primitives     |
| `packages/module-sdk`    | Module manifests, versioned data and content contracts              |
| `systems/cyberpunk-red`  | Independent Cyberpunk RED module scaffold                           |
| `systems/kids-on-bikes`  | Independent Kids on Bikes module scaffold                           |
| `systems/kids-on-brooms` | Independent Kids on Brooms module scaffold                          |

The server serializes mutations and commits before sending updates. Commands have IDs for retry deduplication over the last 10,000 internal revisions; clients do not automatically replay commands after reconnecting. Every HTTP table response, initial/reconnect snapshot, mutation update, and retry response uses a per-member projection. Global revision counters stay on the server. Client views use a content fingerprint computed only from visible fields, and unchanged views are not broadcast when someone else makes a private roll.

Dragging and unfinished strokes are local previews; committed changes synchronize. This first protocol sends complete projected snapshots and is deliberately small. It is not an offline-first or CRDT implementation. Table schema version 4 includes note documents and per-note edit versions. Live protocol **5** adds required scene context and live campaign/scene names to snapshots. Client action frames are `{ context: { campaignId, sceneId, generation }, command }`; the context must match the current campaign and active scene before authorization, deduplication, or mutation. The generation is the public campaign metadata version, not a private-activity/global revision clock. Switching away and back invalidates older actions even when the scene ID is the same. Invalid/stale context never consumes a receipt; stale actions return an error and a fresh filtered snapshot, without automatic replay. **Reload older browser tabs after this protocol upgrade**; context-free commands are rejected. Version 1/2/3 saves upgrade automatically, preserving scene content, internal revisions, command receipts, version 2 ownership, and version 3 private roll visibility. Older rolls remain public; ownerless legacy objects stay GM-controlled. Migrated tables start with an empty notes collection. Unsupported/incomplete saves and ambiguous object IDs fail validation. Reload older browser tabs after upgrading.

Roll retention is separate for the public audience and each private roller: the latest 100 results per audience, at most 1,100 live records overall. Private rolling never evicts public history or another player's private results. Old results in a full audience drop off; archive them manually before they leave live history if you want to retain them. At the overall cap, a new audience must wait until existing live results are archived/deleted. Archives use separate rows and paged reads, hold at most 10,000 results per campaign, and never enter live snapshots. Existing drawing/token/note limits also remain in force; complete snapshots and large-scene performance work remain queued.

SQLite uses Node 24's built-in `node:sqlite` and prepared SQL, behind a validated store boundary. Campaign storage schema 1 separates campaign-wide notes, rolls, and internal revisions from each scene's drawings/tokens. Campaigns have versioned names/descriptions, one active scene, an exact system package version, and exact content-pack pins. Commands have separate receipt namespaces per campaign; scene changes and competing saves reject stale revisions. Limits are 100 campaigns per server and 100 scenes per campaign.

On first startup after this upgrade, the former singleton table and receipts convert atomically to **The gathering place**, preserving the scene, ownership, notes, rolls, edit versions, and receipts. Access identities/sessions/invitations remain intact. Legacy saves had no package version metadata, so this one-time conversion pins the currently installed version of their selected system. Future loads require matching installed system/content-pack versions; missing or incompatible pins fail explicitly instead of silently upgrading or importing arbitrary code. No content packs are shipped yet. This is a one-way storage upgrade: older builds require a pre-upgrade database backup; downgrade and automated package migrations remain unimplemented. The persisted table schema remains 4; live transport is protocol 5.

Access storage schema 1 maps the previous `main` scope to the default campaign UUID. Existing user IDs, names, roles, session/invitation hashes, expiries, invitation IDs, and recovery targets are preserved. Public access contracts now carry a UUID in `tableId`; reload older browser tabs after upgrading. Membership, GM management, invitations, recovery, removal, and credential rotation are scoped to a campaign. A signed-in identity can join an additional invited campaign using `POST /api/access/join` with `keepIdentity: true`; names alone never claim a membership. Anonymous invitation joins still create a new identity, while return codes restore their selected identity. Successful joins and campaign selections replace only the requesting browser session and close its old sockets. Other profiles’ sessions stay in their existing campaigns. The table HTTP/live endpoints resolve their campaign from the session, enforce any supplied `campaignId` query precondition, and never use a client-supplied campaign to choose unauthorized state.

The running server shares one SQLite connection between campaign, access, module-document, and roll-archive stores. Synchronous service transactions can combine campaign/scene creation with access-scope/GM-membership creation atomically; nested store writes use savepoints. Campaign creation uses this boundary to commit its initial scene, access scope, and host membership together. Each live socket is bound to its original credential/campaign/active scene; commands, ownership recipients, receipts, participant counts, and snapshots stay in that campaign. Scene activation pushes fresh context and active-scene data to that campaign without dropping its note drafts. Every mutation checks membership, context, state, and receipts in one SQLite transaction and sends updates after commit. Context includes a public generation, so delayed frames are rejected on old or newly opened connections, including away-and-back scene cycles. Creating an offstage scene and private note/roll activity do not advance that generation or send offstage metadata to players.

This avoids a native package build for self-hosters; normalized campaign/document records currently use explicit prepared SQL. The Node 24 SQLite API may emit an experimental warning.

Modules are trusted installed code, not a sandbox. Each has shared, client, and server entry points and an independent version. Content packs provide stable definition IDs; owned instances carry their own mutable state. Published game data will be added from user-provided sources with edition/page references. Shared Kids-system code should be extracted only after the actual implementations demonstrate common behavior.

## Campaign and scene API

The browser campaign picker and GM scene dialog use these same-origin, cookie-authenticated endpoints. Mutations require the server’s origin. Session credentials are returned only in HttpOnly cookies; invitation codes remain one-use credentials shown separately.

| Endpoint | Access and behavior |
| --- | --- |
| `GET /api/campaigns` | List only the caller’s memberships, with campaign metadata and role. |
| `GET /api/campaigns/:id` | Read metadata only when the caller belongs to that campaign. Nonmembers receive the same unavailable response as unknown IDs. |
| `POST /api/campaigns` | Server host only. Accept campaign settings (`name`, `description`, exact `system` pin, `contentPacks` pins); create the initial scene and host membership atomically. Keeps the current campaign selected. |
| `POST /api/campaigns/:id/settings` | Active campaign GM only. Accept `{ expectedVersion, settings }`; reject stale settings or a different active campaign. System changes update that room’s live views. |
| `POST /api/campaigns/:id/select` | Existing membership only. Accept `{}`; validate the campaign, rotate the current session cookie, and close the previous credential’s sockets. |
| `GET /api/campaigns/:id/scenes` | Active campaign GM only; list scene metadata. Players never receive the offstage list. |
| `POST /api/campaigns/:id/scenes` | Active campaign GM only; accept `{ name }` and create an empty offstage scene. |
| `POST /api/campaigns/:id/activate` | Active campaign GM only; accept `{ sceneId, expectedVersion }`, commit activation, then send the new filtered scene/context to that room. |

Selection never grants membership; use an invitation to join first. Existing GM member/invitation/recovery controls operate in the selected campaign. For a signed-in invitation join that retains the current identity, supply `{ name, code, keepIdentity: true }`; the name is ignored for an existing identity. Failed creation, selection, or joining leaves prior records/credentials intact. Campaign selection and settings are available from the header picker; GM scene creation/activation is available under **Manage scenes**. Activation review becomes stale if another GM changes public campaign settings or the active scene. The basic controls do not yet rename/delete scenes or edit inactive scene content. Campaign/scene lists have an explicit refresh; active names and context update live.

## Module document API

Module-backed documents are separate normalized rows, never included in table snapshots or campaign/scene lists. The current modules validate only provisional `{ name, notes }` data with document schema version 1; they do not implement published character sheets or game rules. Existing plain-text notes stay separate and are not converted. A browser sheet editor and module actions remain queued.

These cookie-authenticated endpoints require the URL campaign to match the session's active campaign. Select the campaign first; supplying an ID never grants membership. Mutations require the server origin. All responses use `Cache-Control: no-store`.

| Endpoint (under `/api/campaigns/:campaignId/documents`) | Behavior |
| --- | --- |
| `GET /` | Visible metadata only, ordered by UUID; optional `after` UUID and `limit` (1–50, default 25). Returns `{ documents, next }`, with `next: null` at the end. |
| `POST /` | Accept `{ title, system: { id, version }, visibility?, data? }`. System pin must exactly match the campaign. Server assigns UUID, owner, schema version, and edit version 1. Missing data uses the installed module factory; visibility defaults to private. |
| `GET /:id` | Fetch one authorized document and validate its stored JSON against the pinned module's current schema. |
| `POST /:id` | Owner/GM only; accept `{ expectedVersion, title, visibility, data }`. Advance the edit version; stale versions return 409. |
| `POST /:id/delete` | Owner/GM only; accept `{ expectedVersion }` and permanently delete. |
| `POST /:id/migrate` | GM only; accept `{ expectedVersion }` and explicitly run the installed module's consecutive schema steps atomically. |

`visibility: "gm"` grants read access to the owner and campaign GMs; `"public"` grants read access to campaign members. Only owner/GM can edit/delete. Visibility is filtered in SQL before payload decoding or pagination. Hidden/foreign document IDs receive the same 404 as unknown IDs. Lists do not expose hidden titles, owner IDs, schema versions, bodies, or totals. Removed members lose access while the GM retains their documents. Private document activity never advances the table revision, campaign generation, or unrelated members' view fingerprints. Documents have no live change events yet: clients must refetch to see edits or access changes. Previously shared content cannot be recalled.

Each campaign is limited to 500 module documents with 120-character titles. Each payload is bounded to 64 KiB of serialized UTF-8 JSON, 10,000 value nodes, and nesting depth 20. Values must be finite JSON; cycles, sparse arrays, accessors, class instances, and silent serialization losses are rejected. Module input and migration outputs pass both JSON bounds and module schema validation. Ownership and package pins are immutable through these endpoints; no ownership-transfer or definition/content-pack catalog API is included.

Document storage schema 1 is independent of campaign/access storage schema 1 and table schema 4/live protocol 5. Every row records its exact system package pin, document `schemaVersion`, and optimistic edit `version`. Server-only module entry points can supply validated consecutive `from → to` schema migrations through `@tableloom/module-sdk/server`. Older document schemas remain listable but cannot be opened/edited until a GM explicitly migrates; absent steps, future schemas, invalid outputs, stale versions, and failed writes leave the row unchanged. Migration hooks are trusted installed code and do not enter the browser. The three scaffolds have no historical schema steps yet; execution is verified with synthetic test fixtures.

This executor handles schema changes within the exact installed package pin; coordinated upgrades to another package version are not implemented. Campaign system/version changes are blocked while incompatible documents exist, including through live `system.set`, so records cannot be stranded silently. Remove those documents or wait for a supported package-upgrade workflow before switching systems. Document APIs have no create retry receipts, history, trash, restore, bulk migration, or sheet UI yet. Roll archive/cleanup controls are available below; broader snapshot-performance work remains queued.

## Roll history and archive

Open **Manage roll history** in **Dice & rolls** to select up to 100 visible results. **Archive selected** moves them out of live history while preserving their exact dice, total, attribution, time, owner, and audience. **Browse archive** reads saved results in pages of 50, with **Next page** and **First page / refresh**. The GM can manage any result; players can archive/delete only their own private rolls. Public results can be removed only by a GM, including public rolls made by a player.

**Delete selected…** opens an explicit review before permanently deleting live or archived results for everyone who could read them. There is no undo/trash. New rolls arriving after selection are not affected; a missing/unavailable selection rejects the entire batch. Refresh/reselect after a stale request. Archives have no automatic retention, restore-to-live, export, chronological search, or live change events yet. Results are paged by UUID, not roll time; archive edits by another member appear after refresh. Archive deletion frees archive capacity; live archive/deletion frees the overall live-history capacity. Removing a member preserves their private archive for the GM. Previously read/downloaded results cannot be recalled.

All endpoints below require a cookie-authenticated active campaign matching the path, validate strict ID-only bodies, enforce the server origin on mutations, and return no-store responses. Hidden/foreign/unknown selected IDs use the same unavailable response. No result contents or global/private history counters are accepted from clients or added to snapshots.

| Endpoint under `/api/campaigns/:campaignId/rolls` | Behavior |
| --- | --- |
| `GET /archive` | Return `{ entries: [{ roll, archivedAt }], next }`, filtered before decoding/paging. Optional `after` UUID and `limit` 1–50 (default 25). No hidden totals. |
| `POST /archive` | Accept `{ ids }` (1–100 unique UUIDs); atomically archive authorized live results and remove them from live state. |
| `POST /delete` | Accept `{ ids }`; permanently remove authorized live results. |
| `POST /archive/delete` | Accept `{ ids }`; permanently remove authorized archived results. |

Roll archive storage schema 1 initializes separately from existing campaign/access/document storage, leaving live table schema 4 and protocol 5 unchanged. Archive insertion and live removal share a transaction, including the saved table revision and receipt; failed writes or capacity checks leave both unchanged. Original dice command receipts remain, so a retry cannot recreate a result after archive/cleanup within the normal receipt-retention window. History operations themselves do not have retry receipts: a repeated successful batch receives unavailable rather than replaying. Live removals send fresh recipient-filtered snapshots after commit; archiving someone else's private results does not change your visible fingerprint or campaign generation. Archive deletion never broadcasts a private activity clock. This is manual history management, not a complete audit log or backup procedure.
